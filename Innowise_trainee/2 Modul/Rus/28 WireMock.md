## Что такое WireMock

**WireMock** — библиотека, которая поднимает тестовый HTTP-сервер и возвращает заранее заданные ответы. Такой сервер называют заглушкой, или stub.

**Цель:** тестировать клиент или сервис без настоящей внешней системы.

WireMock полезен, когда внешний API платный, нестабилен, недоступен в тестовом окружении или слишком медленный.

---

## Когда он нужен

Используй WireMock, когда нужно проверить, как приложение обрабатывает:

- успешный ответ внешнего API;
- ошибку `404`, `429` или `500`;
- медленный ответ или тайм-аут;
- конкретные заголовки, параметры и тело запроса;
- повторные попытки выполнения запроса.

WireMock не проверяет настоящий контракт внешнего поставщика. Для этого нужны отдельные интеграционные или контрактные тесты.

---

## Stub и проверка запроса

Stub задаёт условие запроса и ответ, который вернёт тестовый сервер.

```java
stubFor(get(urlEqualTo("/users/42"))
    .willReturn(aResponse()
        .withStatus(200)
        .withHeader("Content-Type", "application/json")
        .withBody("{\"id\":42,\"name\":\"Ana\"}")));
```

После действия приложения полезно проверить, что запрос действительно был отправлен:

```java
verify(getRequestedFor(urlEqualTo("/users/42")));
```

Проверяй также важные заголовки, query-параметры и тело. Иначе тест может пройти, хотя приложение отправляет неверный запрос.

---

## Запуск в тесте

В JUnit 5 сервер обычно запускают перед тестом и останавливают после него. Адрес WireMock передают в конфигурацию тестируемого клиента вместо настоящего адреса API.

```java
WireMockServer server = new WireMockServer(options().dynamicPort());
server.start();
String baseUrl = server.baseUrl();
```

Динамический порт помогает избежать конфликтов, особенно при параллельном запуске тестов.

## Сценарии ошибок

Хороший набор тестов включает не только успешный ответ:

- `401` или `403` — приложение должно сообщить об отсутствии доступа;
- `404` — правильно обработать отсутствие ресурса;
- `429` — корректно применить повторную попытку или вывести понятную ошибку;
- `500` — не раскрывать пользователю технические детали;
- задержка ответа — сработал ли настроенный тайм-аут.

---

## Типичные ошибки

| Ошибка | Как сделать лучше |
|---|---|
| Заглушка отвечает на любой запрос | Ограничить метод, URL и важные параметры |
| Проверять только результат метода | Дополнительно вызвать `verify()` для запроса |
| Использовать WireMock вместо интеграционных тестов | Сохранять отдельные тесты с реальной системой |
| Оставлять сервер запущенным | Останавливать его в `@AfterEach` или `@AfterAll` |

## Вопросы на собеседовании

### Вопросы начального уровня

**1. Что такое WireMock?**

WireMock — библиотека, которая поднимает тестовый HTTP-сервер и возвращает заранее заданные ответы. Такой сервер называют заглушкой (stub).

**2. Что такое stub в WireMock?**

Stub — правило, которое сопоставляет входящий запрос с условием и возвращает заранее заданный ответ.

**3. Как проверить, что приложение отправило ожидаемый запрос?**

Используй `verify(getRequestedFor(urlEqualTo("...")))` после действия приложения.

**4. Какова цель WireMock?**

Тестировать поведение клиента или сервиса при взаимодействии с внешним API без использования реальной системы.

### Вопросы среднего уровня

**1. Зачем использовать динамический порт для WireMock?**

Динамический порт позволяет избежать конфликтов, особенно при параллельном запуске тестов.

**2. Когда WireMock не подходит?**

WireMock не проверяет настоящий контракт внешнего поставщика. Он не заменяет отдельные интеграционные или контрактные тесты, которые выполняются против реальной системы.

**3. Какие сценарии ошибок должен включать хороший набор тестов?**

401/403 (нет доступа), 404 (ресурс не найден), 429 (лимит запросов / повторная попытка), 500 (ошибка сервера) и задержки ответа (проверка тайм-аута).

**4. Что ещё можно проверить, кроме того, был ли отправлен запрос?**

Заголовки, query-параметры и тело запроса. Без этих проверок тест может пройти, хотя приложение отправляет неверные данные.

### Вопросы повышенного уровня

**1. Почему проверки только результата метода недостаточно при использовании WireMock?**

Метод может вернуть корректное значение, даже если исходящий запрос содержал неверные заголовки, параметры или тело. Вызов `verify()` подтверждает точный запрос, который отправило приложение.

**2. Чем опасна заглушка, которая отвечает на любой запрос?**

Она может скрыть некорректные запросы приложения, из-за чего тест проходит, хотя клиент отправляет неверный URL или метод. Заглушки следует ограничивать методом, URL и важными параметрами.

**3. Почему WireMock не должен заменять интеграционные тесты?**

WireMock имитирует API, но не проверяет реальный контракт. Настоящая система может вести себя иначе — другие статусы, форматы ответов или обработка ошибок. Интеграционные тесты с реальным API выявляют такие расхождения.

### Вопросы с кодом

**1. Что настраивает этот stub?**

```java
stubFor(get(urlEqualTo("/users/42"))
    .willReturn(aResponse()
        .withStatus(200)
        .withHeader("Content-Type", "application/json")
        .withBody("{\"id\":42,\"name\":\"Ana\"}")));
```

**Ответ:** Настраивает сервер WireMock отвечать на `GET /users/42` статусом `200`, заголовком `Content-Type: application/json` и телом `{"id":42,"name":"Ana"}`.

**2. Что проверяет `verify()` в этом примере?**

```java
verify(getRequestedFor(urlEqualTo("/users/42")));
```

**Ответ:** Проверяет, что приложение отправило ровно один `GET`-запрос на `/users/42` во время теста.

**3. Какая ошибка допущена в этом тесте?**

```java
stubFor(any(anyUrl())
    .willReturn(aResponse().withStatus(200)));

// ... действие приложения ...

verify(postRequestedFor(urlEqualTo("/data")));
```

**Ответ:** Заглушка отвечает на любой запрос (`any(anyUrl())`), поэтому даже если приложение отправит неверный URL или метод, оно всё равно получит `200`. Вызов `verify()` упадёт, но до этого приложение могло отправить несколько разных запросов. Заглушки следует ограничивать ожидаемым методом и URL.
