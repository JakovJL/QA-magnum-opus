## 1. Вводные и контекст

**Что за фича.** Customer Wishlist — сохранение вариантов товара «на потом» без добавления в корзину; вторая цель — маркетинговая: узнать самые желанные товары и уведомлять о падении цены и возврате в наличии. `[из описания]`
**Статус:** `Proposed` — «NOT IMPLEMENTED», target «2.23 (**maybe**)», owner Storefront team, **PO: TBD**, Jira-эпик `MEDQA-WISH` помечен как *fake*. Независимое подтверждение вынесения из релиза: `93-release-candidate-2.22.0-rc1.md`, раздел «Not in this release (moved)» → «Wishlist (90) – moved to 2.23». `[из описания]`

**Откуда данные и что подменено.** Задание предполагает входные данные в Confluence. Страница недоступна, вместо неё взято описание фичи из набора Business Requirements песочницы — прямой заменой оно не является: документ короче и грубее. Официальная документация Medusa **не использовалась ни как источник требований, ни как источник утверждений о механике платформы**. Все допущения зафиксированы явно (раздел 2) — это следствие отсутствия PO, а не методический выбор.

**Что реально есть в песочнице.** `[измерено]`

| Факт | Значение для задания |
|---|---|
| Каталог: 4 продукта, 20 вариантов, все €10.00; t-shirt — 8 вариантов (S–XL × Black/White) | Разнообразия товаров и цен для негативных сценариев нет |
| Ровно один регион `Europe`, валюта `eur` | AC цены в валюте региона вырожден |
| `/gb/account/wishlist` → 404; `/store/wishlists*` → 404 | Фичи нет ни в UI, ни в Store API |
| Строка `wishlist` — 0 вхождений в бандлах `/gb/store` | В UI-коде витрины следов фичи нет; сила доказательства ограничена, см. Приложение А.3 |
| `/store/customers/me/*` → 401 **на любой** подпуть; `/admin/*` → 401 на любой путь | 401 не доказывает существование роута; админские эндпоинты неопровержимы без токена |
| Логин и регистрация покупателя работают | Опорная механика для гостевого сценария есть |
| В песочнице **нет ни одного снятого с продажи товара** | Фикстуры под AC-17/AC-18 не существует |

**Ключевое ограничение.** Все 41 критерий приёмки не имеют ни одного подтверждённого прогона. Шаг Verify выполнен частично: он проверил, что я не выдумал сверх описания, и что соседние механики, на которые опираются сценарии, действительно работают. Полноценная сверка возможна только после реализации фичи в 2.23.

## 4. Критерии отбора кандидатов и шкала

**Единое правило направления:** по всем пяти критериям больший балл означает более сильный аргумент **за** автоматизацию. Диапазон единый 1–5; значения 2 и 4 интерполируются между якорями 1 / 3 / 5.

| # | Критерий | Отражает | 1 | 3 | 5 | Измерим в песочнице |
|---|---|---|---|---|---|---|
| **F** | Частота выполнения | выигрыш | проходит раз в месяц и реже; ручной прогон занимает минуты | раз в неделю в регрессии | входит в каждый прогон и каждый релиз | **Нет** → допущение |
| **C** | Цена пропуска дефекта | выигрыш | косметика; выручка, данные и доверие не затронуты | заметная проблема UX, обходной путь есть | потеря денег, данных или приватности; клиент не может совершить покупку | **Нет** → допущение |
| **S** | Стабильность и зрелость фичи | стоимость и риск | поведение не зафиксировано, часть AC противоречива, фича в статусе Proposed | поведение зафиксировано, но реализация молодая и будет меняться | поведение зафиксировано, покрыто однозначными AC, меняется только по согласованному изменению | **Частично да** — по состоянию описания и сборки |
| **A** | Простота автоматизации и детерминированность | стоимость | нужны сложные фикстуры, внешние сервисы, недетерминированные данные; локаторы нестабильны | линейный сценарий, один-два фикстура, стабильные локаторы | чистый детерминированный сценарий, данные создаются через API, локаторы по стабильным атрибутам | **Нет** → допущение |
| **U** | Устойчивость к ложным падениям | риск | заведомо флейкает; каждое падение требует ручного разбора | флейкинг редок, причина понятна | детерминированный прогон, ложных падений нет, сигнал однозначен | **Нет** → допущение |

**Покрытие аспектов:** выигрыш — F, C · стоимость — A, S · риск — U, S.

### Правило перехода к вердикту (задано до оценки)

Сумма пяти критериев, диапазон **5–25**.

| Сумма | Вердикт |
|---|---|
| **≥ 19** | **must automate** |
| **12–18** | **nice to have** |
| **≤ 11** | **not worth it** |

Обоснование порогов: при пяти критериях ≥19 означает средний балл ≥3,8 — сценарий должен быть сильным почти по всем осям, а не ярким по одной. 12–18 (среднее 2,4–3,6) — «сделать, если дойдут руки». ≤11 (среднее ≤2,2) — вручную дешевле.

1. **Правило ничьей.** При равных суммах приоритет отдаётся сценарию с **более низким S**: автоматизация незрелой фичи — типовая ошибка, и сумма не должна её маскировать.
2. **Правило допущения.** Если хотя бы один вход сценария — допущение, вердикт помечается предварительным.
3. **Правило непроверенности (кап).** Сценарий **не может** получить `must automate`, пока хотя бы одна его AC не подтверждена хотя бы одним прогоном в среде.
4. **Окно пересмотра.** Оценки, сделанные до реализации, пересматриваются после появления фичи.

**Следствие для текущего момента:** 4 из 5 критериев не измеримы в песочнице, единственный измеримый критерий S — измеримо низкий (статус `Proposed`, три AC с незакрытыми развилками, схема помечена `proposal`, фичи нет в сборке). Правила 2 и 3 в совокупности означают, что **`must automate` сегодня недостижим ни для одного сценария**. Это следствие того, что автоматизировать нечего, а не дефект методики.

### А.3 Методологические слабости доказательной базы

1. **`snapshot -i` показывает только интерактивные элементы.** Иконка без корректной ARIA-семантики в такой снапшот не попадает. Для утверждения об **отсутствии** нужен полный снапшот или запрос к DOM.
2. **Поиск строки по бандлам не видит route-level code splitting.** Я сканировал 20 чанков, подгружаемых на `/gb/store`. Маршрут `/account/wishlist` в App Router — отдельный чанк, в выборку не входивший.
3. **401 на защищённом префиксе не доказывает существование роута.** Префикс `/store/customers/me` и `/admin` отдают 401 на любой подпуть. Единственный надёжный вывод — о **невозможности** проверки, а не о наличии или отсутствии маршрута.
4. **Ключ, извлечённый из клиентского бандла, не равен тому, с которым работает приложение.** Все отрицательные API-выводы корректны, но ограничены каналом этого ключа (см. П-12 и Приложение В).

## Приложение Б. Пять правок промпта на следующий раз

1. **Правило источника для обоснований.** «Каждая оценка в матрице сопровождается ссылкой на источник — цитату описания или номер замера в песочнице. Если основание не подтверждено ни тем, ни другим, пометь его как гипотезу и не используй для повышения балла».
2. **Правило пути доступа.** «Состав каталога и любые выводы об отсутствии собирай тем же путём, который использует приложение (по сетевым запросам страницы), а не ключом, извлечённым из клиентского бандла; после каждого отрицательного API-вывода явно оговори область действия — какой sales channel или ключ он покрывает».
3. **Правило проверки метода.** «Прежде чем утверждать, что чего-то нет, назови инструмент, которым это доказывается, и проверь его на ложноположительность. Интерактивный снапшот не видит несемантические элементы; поиск по бандлам не видит route-level code splitting; 401 на защищённом префиксе не доказывает существование роута — нужен контрольный запрос на заведомо несуществующий путь».
4. **Правило отсутствующих AC.** «Если у истории нет критериев приёмки — выводи их из имеющихся фактов описания и помечай, какая часть достроена тобой. Не предлагай исключить историю из охождения: по правилу задания каждый пункт описания обязан быть закрыт критерием».
5. **Правило для неизмеримого.** «Перед выводом "в песочнице нечем мерить" перечисли, какими средствами это проверяется прямо сейчас — публичным ключом, витриной, существующим фикстуром. Если средства есть, проверь, а не объявляй замер невозможным».
