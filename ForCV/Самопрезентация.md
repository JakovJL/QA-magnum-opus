## Текущий проект

My current project is a B2B knowledge assistant for customer support teams. I've been working on it since October 2024. An operator asks a question. The system finds the documents that this operator is allowed to see and prepares a draft answer with links to the sources. The operator checks and edits the draft, and then sends it. The assistant never writes to the customer and never changes an order.

The risk starts after the draft is ready. The operator sends it to a real customer. If the answer is based on an old rule, or on a rule from another company, the customer gets the wrong answer — and the company is responsible for it.

To give you an idea of the size: about 900 operator accounts, around 15,000 documents, and peak load around 20 requests per second. But real answer generation is much lower — about two per second.

## Архитектура

There are two independent flows.

The first flow is document preparation. An approved file goes to S3. A record and an indexing job go to PostgreSQL. A background worker splits the text into chunks. Then it gets embeddings for the chunks. After that, it turns on the new version — all at once. Until this finishes, search still uses the old version.

The second flow is the answer. The operator asks a question. The assistant API takes the tenant and roles from the server context, not from the browser. It calls the knowledge service. The knowledge service returns only the chunks this user can see. The question and these chunks go to the external LLM. The LLM returns a draft with links. The API checks every link against the chunks it really got.

We check permissions twice: when retrieval selects documents, and again when a user opens a source.

## Ответственность

My part is the Java automation around both flows, plus the evaluation layer. Together with a support expert I maintain the reference set: questions, expected facts and allowed sources.

## Достижения

Two things I want to highlight.

The first is an access-control issue. A support agent asked about an internal rule. Only a manager could see this rule. The answer had no link to the document, but the rule itself was in the answer. I checked what retrieval selected and what went to the model. The restricted text was in the context. The permission filter worked later — it only checked the list of links. So the filter was in the wrong place. The developer moved the check into retrieval, before the model call. I added regression tests: agent and manager, two organizations, direct access by document ID, and attempts to change the tenant in the request. I also checked that the manager still has access.

The second is the split between technical regression and answer quality. Green API tests show that the contract works and that the app handles a mocked model. They do not show that the answer is correct. So we split the checks. WireMock for contracts, timeouts, 429 and malformed responses. A golden set of 60 questions with expected facts and allowed sources for the content, with the real model on stage. This changed the release talk. Before, we said "the build is green". Now we can say which layer failed: integration, retrieval or generation.

## Подробный кейс: закрытый документ повлиял на ответ AI

One of my strongest cases was around access. I was testing the assistant with users in different roles. There was a document with an internal rule — only a manager could see it. And a support agent asks about exactly that rule. The document link was not in the answer, but the rule itself was.

So I went to check what was sent to the model. And I saw: the restricted text was going into the context, and the permission check ran later — only on the list of links. The filter was in the wrong place.

The developer moved the permission check into document retrieval, before the model call. On my side, I covered it with regression: the agent and the manager, different organizations, direct access to the document, attempts to substitute IDs. And I checked that the manager with the right permissions keeps access.

In the end — a reproducible scenario and a set of checks. I don't claim a real leak or the number of affected users.
